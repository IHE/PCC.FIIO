The goals of testing the IPS are: 
- Test the document generated by the Content Creator system for conformance to the HL7 FHIR IPS document and any additional implementation options chosen for the test. 
- Test that the Content Consumer system is able to consume the IPS document and implementation option in one of the accepted formats: FHIR View, Document Import, Discrete Data Import, or Complete Discrete Data Import. These options are chosen by the Content Consumer system at registration. 

### Testing Expectations

#### Obligations and Data Absent Reasons 
For all sections and elements with a populate-if-known obligation, the system under test is required to express data it cannot access as unavailable, rather than implying by omission that the data is not relevant. 

If there is no relevant information provided for a populate-if-known obligation on a section or element, the section **MAY** be omitted, and no data absent or empty reason is expected. 

If the system does not have access to data to populate a populate-if-known obligation section or data element, it **SHALL** contain a data absent/Empty Reason indicating why the information is unavailable. This is a patient safety requirement to identify that the information cannot be assumed empty or irrelevant. This can be achieved using the Unavailable code for an [Empty Reason](http://terminology.hl7.org/CodeSystem/list-empty-reason) at the Section level or an appropriate [Data Absent Reason](https://hl7.org/fhir/R4/valueset-data-absent-reason.html) at the Entry level. This distinguishes unavailable data from data that a mediator intentionally omitted as not relevant.

**populate-if-known**
There are many elements within this profile that have the populate-if-known Obligation for the Content Creator system. During testing, the Content Creator system will be provided with test data that includes content for each of these testing obligations and will be required to demonstrate conformance with the IPS obligations. 
- Systems will be surveyed for the attributes managed by the system under test.   
- All systems will be required to include content labeled with this obligation at every level when generating the IPS. For instance, the IPS Condition.code.coding has a SHALL:populate-if-known obligation noted in the Data Type Profile requirements. This will be reviewed during testing, and elements at all levels will be expected to be populated in accordance with the obligation requirements. 
- For elements that were identified as not supported by the system under test, the generated IPS is expected to include an appropriate data absent reason. For a system that does not support the entries of a section with a populate-if-known obligation, the section is expected to be present with an emptyReason of unavailable.
- All systems will undergo visual inspection along with a review of the validator output to ensure all expected data is populated or an appropriate data absent reason is provided where the known data is expected in the generated IPS document. 

**Handling** 
There are many elements within this profile that have the Handling Obligation for the Content Consumer system. During testing, the Content Consumer system will undergo visual inspection to review that the handling expectation is achieved.
- For systems that support these elements, the elements will be imported.
- For systems that do not import or store these elements, there **SHALL** be an ability to display the information or highlight to the user that the data is missing and therefore unknown. 

Proof of handling can be done through the following Content Consumer Options:
- Document Import
- Discrete Data Import

**Display** 
There are many elements within this profile that have the Display Obligation for the Content Consumer system. During testing, the Content Consumer system will undergo visual inspection to review that the Display expectation is achieved.
- All systems will be expected to display all the human-readable information for elements labeled with the display obligation. For instance, the IPS Condition.code.text has a display obligation noted in the Data Type Profile requirements. This will be reviewed during visual inspection.

#### Test Patient Data 
Systems will be provided with a predetermined set of data expectations that SHALL be met before arriving at the testing event. 

Several patients for the testing options will be provided with the expected information that **SHALL** be entered into the patient record in the Content Creator system. 

The patient information will range from a complex patient record to a simplistic one to properly test the implementation of the Required and Required If Known sections. This also applies to testing the Obligation requirements.   

Sample patient records may be provided if the testing system would rather import predetermined patient information.

   - For the Occupational Data for Health Option
     - The system under test will be required to document which data elements supporting the Occupational Data for Health Option concepts can be collected and maintained within the product.
   - For the Complete Option
     - The system under test will be required to document which data elements supporting the Complete Option can be collected and maintained within the product. 

2. Data will be provided for all required sections and data elements such that the system under test will be able to demonstrate inclusion of these concepts within the IPS document generated in the subsequent tests. Screenshots should be provided to show that the data has been added to the patient's record within the system. 
   - For the Occupational Data for Health Option
     - Data will be provided for all data elements supporting the Occupational Data for Health Option.
   - For the Complete Option
     - Data will be provided for all data elements supporting the Complete Option.

3. This is a no-peer test.

#### Content Creator Document Check Test
1. The Content Creator system will generate an IPS for the patient(s) provided in the Add Patient Records Test that includes all must support and required concepts. This IPS will be validated using the IHE External Validation Tool.
2. The Monitor will visually inspect to verify that all must support and required concepts documented in the Add Patient Records Test as collected and maintained within the product are included in the validated IPS.
3. This is a no-peer test. 

#### Content Creator ImportExport Test
1. The Monitor verifies that a validated IPS document is successfully generated by the Content Creator. 
2. The Monitor verifies that the Content Consumer is able to consume the document provided by the Content Creator using at least one of the Content Consumer options (FHIR View, Document Import, Discrete Data Import, Complete Discrete Data Import). 
3. No transport is required for this test.   
4. This is a peer-to-peer test between a Content Creator and Content Consumer.

#### Testing Approach for National Extensions
National extensions for IPS, such as [US-PCS](volume-4.html#usa-nationalExtension) and [PS-CA](volume-4.html#canadian-nationalExtension), are implemented on top of the HL7 FHIR IPS, not instead of it. A Content Creator implements the [HL7 FHIR IPS 2.0.1](https://hl7.org/fhir/uv/ips/) first, and then applies the additional constraints of the national extension.

When a Content Creator tests a national extension for IPS at an IHE Test Event, the system under test SHALL:
1. Pass validation of the generated document against the [HL7 FHIR IPS Bundle](http://hl7.org/fhir/uv/ips/StructureDefinition/Bundle-uv-ips) first, including any implementation option the system claims (Complete or ODH).
2. Then pass validation of the same document against the national extension Bundle (for example, the US-PCS Bundle or the PS-CA Bundle).

A document that passes the national extension but fails the HL7 FHIR IPS validation does not pass the test.

The [National Extensions](volume-4.html) tables describe each difference in the Notes column:
- **Constrained**: the national extension is stricter than IPS (higher cardinality, added Must Support, constrained target profile, etc.). Satisfying it does not break IPS conformance.
- **Added**: the national extension adds an element, section, or extension that IPS does not define. IPS permits it through open slicing.
- **De-constrained**: the national extension is less strict than IPS (lower cardinality, removed Must Support or obligation). A document that only meets the national extension may fail the IPS validation. Appropriate reasoning and regional limitations may be submitted during the testing event for exceptions. 

Where a national extension de-constrains an IPS requirement, the IPS requirement applies during testing. For example, US Core makes Patient.birthDate optional, but IPS requires it, so the IPS requirement applies. However, regional limitations may be waived. For example, PS-CA does not flag Patient.generalPractitioner as Must Support while IPS does, so the system under test may receive an exception due to regional limitations around general practitioner data collection.

A validator with the national extension package and its dependencies (for example, US Core and the FHIR Clinical Document IG for US-PCS, or the CA Baseline for PS-CA) will be provided. 

#### Content Creator National Extension Document Check Test
1. The Content Creator system will generate an IPS for the patient(s) provided in the Add Patient Records Test, following the national extension it registered for.
2. The document will be validated against the HL7 FHIR IPS Bundle using the IHE External Validation Tool. Errors SHALL be resolved before continuing.
3. The same document will be validated against the national extension Bundle. Errors SHALL be resolved, or appropriate reasoning and regional limitations must be submitted for review.
4. The Monitor will visually inspect the document to verify that the required elements are populated when the system supports them, or carry an appropriate data absent or empty reason.
5. This is a no-peer test.

#### Content Creator National Extension ImportExport Test
1. The Monitor verifies that a validated IPS document that conforms to the national extension is successfully generated by the Content Creator. 
2. The Monitor verifies that the Content Consumer is able to consume the document provided by the Content Creator using at least one of the Content Consumer options (FHIR View, Document Import, Discrete Data Import, Complete Discrete Data Import). 
3. No transport is required for this test.   
4. This is a peer-to-peer test between a Content Creator and Content Consumer.
